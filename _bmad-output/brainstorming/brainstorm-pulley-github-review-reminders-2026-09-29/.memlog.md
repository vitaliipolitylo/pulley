- (direction by user) Build a small VS Code extension named Pulley to help developers notice GitHub pull requests awaiting their review.
- (idea by user) A corgi mascot changes expression and message for new, aging, multiple, and completed review requests.
- (direction by user) MVP should connect to GitHub, find PRs requesting the current user, check periodically, indicate waiting reviews, and open PRs from VS Code.
- (direction by user) Explore realistic VS Code UI options without committing early to a particular surface.
- (direction by user) Primary goal is to learn BMAD from idea through implementation and gradually expand integration and AI engineering skills.
- (decision by user) AI summaries, risk detection, focus suggestions, assisted reviews, and prioritization are future possibilities outside the initial MVP.
- (direction by user) Creative Partner mode; use Yes And Building, Role Playing, then Reverse Brainstorming.
- (technique) started Yes And Building
- (idea by coach) A small at-a-glance review signal could lead to a short list of waiting PRs, with Pulley expression reflecting the current queue.
- (idea by user) The first signal should be a notification that informs about a waiting PR without becoming annoying.
- (idea by coach) Notify once when a new review request appears; let an ambient queue reflect continuing or aging requests without repeated interruptions.
- (idea by user) The new-review notification should show the name of the user who requested the PR review.
- (decision by user) Prefer the person who requested the review when easy to obtain; otherwise show the PR author.
- (insight by coach) GitHub review-requested timeline events carry an actor and requested reviewer; requester display may require an additional per-PR timeline lookup.
- (direction by user) Pulley should feel like a friendly reminder rather than a strict call to action; that is the mascot's meaning.
- (idea by coach) Use gentle notification language such as 'Pulley spotted a review from Maya' with an optional Open PR action.
- (decision by user) After the first notification, an unhandled review should remain in a quiet place with an unread-style mark instead of generating another interruption.
- (idea by coach) Keep a persistent low-noise marker for pending reviews, potentially a dot or count that opens the waiting list.
- (direction by user) User is unsure which VS Code surface is best; sidebar or panel near Copilot are possibilities to explore.
- (insight by coach) VS Code supports extension status bar items, activity bar view containers, and movable sidebar/panel views; TreeView has a numeric badge property.
- (technique) started Role Playing
- (idea by user) Let users configure where Pulley appears in VS Code.
- (idea by user) Opening Pulley should show open PRs waiting for the current user's review.
- (insight by coach) VS Code users can move a contributed view between sidebars and panel through native layout controls; an explicit placement setting may be unnecessary for the first version.
- (idea by user) The waiting-PR list could show labels, author, direct link, source branch, and target branch in addition to title.
- (decision by user) The compact PR list should visibly show title, author, and time; labels and branch details need not occupy each row.
- (decision by user) Time in the PR list means elapsed time since the current user's review was requested, not PR age.
- (technique) started Reverse Brainstorming
- (idea by coach) Failure mode: Pulley keeps a review visible after it was completed, removed, or closed, making the queue feel untrustworthy.
- (idea by user) A large number of waiting PRs could break Pulley or make it unusable.
- (idea by coach) Failure mode: on first connection with many existing requests, Pulley floods the developer with one notification per PR.
- (idea by user) For a large backlog, use one playful aggregate message such as 'Pulley is covered in PRs. Help him!'
- (idea by coach) On first connection, summarize an existing backlog in one message and let the queue carry individual PR details.
- (insight by user) Failure mode: Pulley may be so gentle that developers fail to notice or act on waiting reviews.
- (idea by user) When VS Code opens and reviews have piled up, Pulley could show an aggregate backlog message.
- (idea by coach) A startup summary could be a second chance to notice an aging backlog, provided it is capped so reopening windows does not repeatedly interrupt.
- (decision by user) A backlog reminder at VS Code startup should appear no more than once a day.
- (idea by user) Pulley should have several distinct pile-up messages rather than repeating the same line.
- (idea by coach) Use a small hand-written set of context-specific backlog lines, rotating them without requiring AI.
- (decision by user) Default pile-up threshold is five waiting PRs.
- (idea by user) The pile-up threshold could be configurable in VS Code settings.
- (question by coach) Would configurable pile-up thresholds solve a first-release need or add avoidable settings complexity?
- (insight by user) A team may have a norm of keeping no more than three PR reviews waiting, making a configurable pile-up threshold useful.
- (insight by coach) A threshold should signal the user's chosen backlog level without turning Pulley into a performance monitor.
- (decision by user) Initial scope is the GitHub repository associated with the current VS Code workspace.
- (decision by user) Support for multiple repositories is a future possibility outside the first version.
- (decision by user) When the workspace has no connected GitHub repository, Pulley should explain that the project is not connected to a repository.
- (insight by coach) VS Code has a built-in GitHub authentication provider and Git extension API that can expose workspace repositories/remotes.
- (insight by coach) GitHub search supports direct user review-requested filtering; exact request age and requester identity are available from per-PR timeline events, which add API calls.
- (insight) The product promise is a friendly, trustworthy review reminder: one timely new-request notification, then a quiet persistent queue.
- (insight) The mascot's state and message cadence are linked: excitement for new work, overwhelmed copy for backlog, and resting when clear; personality should never create notification spam.
- (insight) Large-backlog handling combines one aggregate message, a once-per-day startup ceiling, rotating hand-written copy, and a default threshold of five with a setting motivated by team norms.
- (insight) First-release scope centers on one GitHub repository tied to the current workspace, with a clear disconnected state and a compact list of title, author, and time waiting.
- (insight) Requester identity and exact time since review request can come from timeline events; whether their extra API work belongs in MVP remains a product decision.
- (insight) Trust depends on timely removal of completed, withdrawn, or closed requests and graceful handling of large queues; AI review features and multi-repo support remain future possibilities.
