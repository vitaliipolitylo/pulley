How Pulley works

A VS Code extension that tells you once when someone asks for your review, then keeps a quiet, accurate queue until the request is gone. This page walks through how it is built and why.

The one idea

All of Pulley's rules live in one pure function. It takes what Pulley remembered, what GitHub just said, and the current time. It returns what Pulley should remember next and which notifications to show. Everything else is plumbing.

That function is reconcile. It never touches the network, the disk, the clock, or VS Code. So every tricky rule ("alert once", "don't alert for requests that arrived while VS Code was closed", "one reminder per day", "a failed check is not an empty queue") can be tested with a plain table of inputs and expected outputs. This design is called functional core, imperative shell.

Two halves

Core decides, shell does

Core · src/core/

Pure TypeScript. No vscode import, no I/O, no clock, no randomness.

  • The stored state's shape and migrate
  • reconcile: applies a check result
  • queueViewed, windowFocused: UI events
  • viewModel: what the view and count show
  • copy.ts: every word the user reads

Shell · src/shell/

Thin adapters that talk to the outside world and do what core says.

  • github.ts: one GraphQL search per check
  • auth.ts: VS Code's built-in GitHub sign-in
  • store.ts: the only code that writes state
  • scheduler.ts: when checks run
  • notifier.ts, queueView.ts, statusCount.ts

End to end

What happens during one check

  1. Something triggers a check: VS Code finishing startup, the 15-minute timer (with a little random jitter), the Refresh button, or a sign-in change. Opening the view doesn't trigger one.
  2. The GitHub adapter asks one question: is:pr is:open user-review-requested:@me archived:false. For each PR it also pulls the latest "review requested" events to learn who asked and when. If that can't be matched, the row says "Request time unavailable" instead of guessing.
  3. The result is normalized into a GitHub-agnostic CheckResult, stamped with when the fetch started and whether every page came back.
  4. store.mutate re-reads state fresh, since another window may have written since, and hands it to reconcile.
  5. reconcile decides: which rows to add or remove, whether each new one is "new" or "backlog", whether a reminder is due, and which alerts are pending.
  6. The new state is saved first. Only after the write completes are notifications shown, and only in the window you're using. Then the view re-renders if anything visible changed.

The lifecycle

A review request's life inside Pulley

A request is tracked by its pull request's GitHub ID, so renaming a repo doesn't make it look new. It stays in the queue until a complete, successful check no longer contains it. A failed or partial check never removes anything.

stateDiagram-v2
  [*] --> NewPending: first seen while Pulley was running
  [*] --> Backlog: first check ever, or Pulley was away
  NewPending --> NewShown: shown in the focused window
  NewPending --> [*]: complete check no longer has it
  NewShown --> [*]: complete check no longer has it
  Backlog --> [*]: complete check no longer has it

"Pulley was away" means the gap since the last attempted check is more than twice the check interval. That covers VS Code being closed and a laptop asleep, but not a Wi-Fi drop while you keep coding, because failed checks still count as attempts.

Trade-offs

What we chose, and what it cost

DecisionInstead ofWhat we gain / what we give up
Pure core, thin shellFeature classes calling each otherOne place decides every alert, and it's unit-testable. Needs discipline to keep I/O out of core.
Account-wide requestsOnly the open workspace's repo (the PRD's original scope)No repo detection, and it works in any window. Rows need a repo label; orgs that block VS Code's sign-in silently drop out. The PRD and UX need updating.
One GraphQL query per checkREST search plus a timeline call per PRA single round trip that includes who asked and when. A spike must confirm the event matching on real repos.
repo sign-in scopeA GitHub App with read-only permissionsUses VS Code's built-in sign-in, with no tokens stored by Pulley. The permission prompt looks broader than what Pulley actually reads.
Alerts only in the focused windowEvery window alerts, or a cross-window lockNo routine duplicates, and alerts land where you're looking. If you're away from VS Code, the alert waits for you.
15-minute pollingWebhooks or faster pollingNothing to host, and it's gentle on GitHub's rate limits. A request can take up to about 16 minutes to show up.
No telemetryUsage analyticsOnly GitHub ever sees a request. Dogfood learning comes from conversations and the local log.
Reference

The fifteen rules, in one line each

Stories cite these by ID. Full wording is in ARCHITECTURE-SPINE.md.

AD-1Core is pure

No VS Code, I/O, clock, randomness or timers under src/core. Time is passed in.

AD-2Core transitions are the only deciders

reconcile, queueViewed and windowFocused return the next state plus effects. Effects are only notifyNew and notifyBacklog.

AD-3One write path

store.mutate re-reads, applies, awaits the write, then acts. A window seeing a newer schema goes read-only.

AD-4Stored state shape

One globalState record, everything partitioned per GitHub account; window-only facts are never persisted.

AD-5Check result contract

Normalized, timestamped, marked complete or not. Older and partial results can't undo newer truth.

AD-6Identity and cycles

Keyed on PR node ID. A cycle ends only when a complete successful check omits it.

AD-7New vs. backlog

Backlog on the first check ever or after a gap of more than 2× the interval since the last attempt; otherwise new and alert-pending.

AD-8Backlog reminders

Once on first connection; afterwards at most once per local day, surviving a failed startup check.

AD-9Focus-gated delivery

Every window records pending alerts; only the focused window shows them and marks them shown.

AD-10One GraphQL search per check

Account-wide direct requests, paged to the end, with per-item fallback for requester and time.

AD-11Authentication

Built-in GitHub sign-in, silent at startup, a prompt only when you click Connect; a single silent retry on 401.

AD-12View model contract

One status, a count that stays blank until the first successful check, mascot precedence, all copy from copy.ts.

AD-13Failure is not emptiness

A failed check changes only failure bookkeeping, never the queue or alert history.

AD-14Activation and scheduling

Starts on onStartupFinished; one check in flight per window; jittered timers; bounded settings.

AD-15Minimal data leaves the machine

Only api.github.com. No telemetry, and tokens are never logged.
